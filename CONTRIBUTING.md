# Contributing to BeatForge

Thanks for your interest! BeatForge is built to be approachable both for human contributors and for Copilot agents working via Copilot CLI or the Copilot coding agent.

## Ground rules

1. **Privacy first.** Read [`PRIVACY.md`](PRIVACY.md). Any change that touches audio I/O, network code, or the no-audio-egress harness needs an explicit review against the privacy policy.
2. **License is Apache-2.0.** By submitting a contribution, you agree to license it under Apache-2.0 (see [`LICENSE`](LICENSE)).
3. **Issues drive work.** Every PR should reference an open issue. The issue defines the scope, files to touch, validation steps, and network policy.
4. **REAPER-ready, always.** Any change that produces a `.mid` artifact must keep it REAPER-importable: GM drum notes, channel 10, tempo + time-signature meta events present.
5. **Deterministic by default.** Rules-based code paths must be byte-stable for the same inputs + same `--seed`. ML code paths must be structurally stable (see `ROADMAP.md` § Determinism policy).

## Workflow

1. Pick or open an issue. If none fits, propose one before writing code.
2. Create a feature branch off `main` named `feat/<short-slug>` or `fix/<short-slug>`.
3. Implement the change. Add or update tests in `tests/`.
4. Run the full local check before pushing:
   ```bash
   ruff check .
   ruff format --check .
   mypy src
   pytest -q
   pytest -m no_network
   ```
5. Open a PR. Fill in the template. Link the issue with `Closes #N`.

## Project layout (target)

```
src/beatforge/          # library code
src/beatforge/cli/      # drumgen CLI entrypoints
src/beatforge/audio/    # local audio analysis (librosa/madmom)
src/beatforge/midi/     # MIDI read/write/validate
src/beatforge/models/   # symbolic groove model adapters
src/beatforge/privacy/  # no-egress harness, network policy
tests/                  # pytest tests, including no_network suite
examples/               # end-to-end usage examples
docs/                   # extended docs (architecture, schemas)
```

## Working with Copilot agents

See [`AGENTS.md`](AGENTS.md) for the full instructions. In short:

- Every issue is written so it can be executed by a Copilot agent without manual gap-filling.
- Issues must include: files to touch, commands to run, artifacts produced, validation steps, and explicit network policy.
- If a Copilot agent encounters ambiguity it cannot resolve from the issue text + repo state, it should comment on the issue rather than guess.

## Commit messages

Conventional Commits style is preferred:

- `feat: add drumgen analyze command`
- `fix(midi): preserve tempo meta on edit`
- `docs: clarify no-audio-egress test plan`
- `chore: bump ruff to 0.x.y`

Do **not** include AI-authorship trailers (`Co-authored-by: Copilot`, `Generated by AI`, etc.). The committing author is responsible for the change.
